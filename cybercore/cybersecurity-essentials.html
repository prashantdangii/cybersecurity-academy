The path

    Rule

    01concept · check

    CIA triad

    Concept

    Every control and every incident maps to at least one of these. If you can’t name which, you don’t understand the impact yet.

    CConfidentiality — who can see it
    IIntegrity — was it changed
    AAvailability — can we use it

    Breaks

    • C — data leak, stolen laptop, mis-share
    • I — ransomware encrypt, poisoned update
    • A — DDoS, disk full, deleted backups

    Controls

    • C — encryption, access control, DLP
    • I — hashing, signing, least privilege
    • A — redundancy, backups, rate limits

    02concept · check

    Threat, vuln, risk

    Concept

    Risk needs a threat that can exploit a vulnerability against an asset — with impact. No exploit path ⇒ noise, not risk.

    Assetwhat you care about
    Vulnerabilityweakness
    Threatwho/what can abuse it
    Risklikelihood × impact
    • Threat — ransomware crew, insider, flood
    • Vulnerability — unpatched CVE, weak password
    • Risk — chance of loss + how bad
    • Control — reduces likelihood or impact

    06concept · check

    Authn vs authz

    Concept

    Authentication = prove identity. Authorization = what that identity may do. Most “IDOR” bugs are authz failures.

    Authn fails

    • Password spray succeeds
    • Session stolen (cookie theft)
    • MFA bypass / prompt bombing

    Authz fails

    • User A reads User B’s /invoices/42
    • Support role can delete prod
    • API trusts client-side “isAdmin”
    • MFA — harder authn
    • Least privilege — tighter authz
    • Session — proof after login
    • RBAC / ABAC — authz models

    Check yourself

    Logged-in user changes ?id=100 to ?id=101 and sees another user’s data. Bug type?

    07concept · terminal · check

    Crypto must-knows

    Concept

    Wrong tool = false safety. Hash for integrity/passwords (with salt+slow KDF). Encrypt for confidentiality. Sign for authenticity.

    Hashone-way fingerprint
    Encryptreversible with key
    Signprove origin
    Password storage

    Never “encrypt passwords” for login stores. Use a password hash (bcrypt/argon2/scrypt) — not plain SHA-256 alone.

    Mission terminal

    MissionPick the right primitiveCommands: hash | encrypt | sign — match the scenario prompts
    scenario · cryptolive
    crypto@lab:~$

    • Store a password verifier → hash
    • Protect a file at rest → encrypt
    • Prove a release is from you → sign
